# AgentPorter 方案总览

## 1. 项目定位

**项目名：AgentPorter**。

AgentPorter 专门处理“把一组分层 Worker/子代理定义，安全地移植到不同 Agent 平台和不同主机”这一类工作。名称强调的不是创建一个新的 Agent 运行时，而是把已经确定的角色、边界和模型偏好搬运成目标平台能理解的原生配置。

## 2. 问题定义

不同平台通常同时存在以下差异：

- 配置位置不同，例如用户级目录、项目级目录或独立 Profile；
- Agent 的注册方式不同，例如目录自动发现、主配置显式注册、命令行 Profile 或任务队列 assignee；
- 字段不同，例如 `instructions`、`developer_instructions`、`SOUL.md`；
- 模型和 reasoning 的可覆盖粒度不同；
- 全局可见性和工作区继承规则不同；
- 有的平台支持命名子代理，有的平台只能统一设置 delegation 模型。

因此，项目不能把某个平台的 TOML 当成通用标准。正确分层是：

```text
平台无关 Worker 清单
        ↓
语义校验与能力协商
        ↓
平台 Adapter
        ↓
目标文件计划与 diff
        ↓
用户确认/非破坏安装
        ↓
目标平台原生验证
```

## 3. 核心原则

### 3.1 语义先于格式

`workers.yaml` 是职责和边界的权威输入；Codex TOML、Hermes Profile 等均为派生物。平台文件可以不同，但不得弱化以下不变量：

1. Worker 不得改变主任务目标；
2. Worker 不得自行扩大工作范围；
3. `codex_5_3_small_worker` 只能接收比 `luna_worker` 更简单、更机械的任务；
4. 缺少必要细节时必须报告阻塞，不得靠扩大范围补齐；
5. 具体模型不可用时必须明确报错或要求显式 fallback，不得静默换模型。

### 3.2 非破坏安装

- 默认只生成预览，不直接写入；
- 写入前保存受影响文件的快照；
- 只管理项目明确拥有的文件或带标记的配置段；
- 不删除未知 Agent、不重写整份用户配置；
- 安装后运行平台原生解析/诊断命令；
- 验证失败时恢复快照。

### 3.3 能力协商而非虚假等价

每个 Adapter 必须声明目标平台是否支持：

- 命名 Worker；
- 每 Worker 独立模型；
- 每 Worker 独立 reasoning；
- 独立 instructions；
- 用户级全局可见；
- 项目级覆盖；
- 原生配置验证；
- 自动任务路由。

不支持的能力必须出现在兼容性报告中。Adapter 可以提供替代方案，但不能宣称“完全等价”。

## 4. 首批 Worker

### Luna Worker

用于目标、范围、文件和验收细节已经由主代理敲定的补全型任务。它可以进行有限推理和实现，但不能重设目标、引入邻近需求或做未授权的架构决策。

### Codex 5.3 Small Worker

仅用于极简单脚本、巨大日志或工具输出的读取筛选，以及按非常具体规则执行的批量文件更新。它是机械层 Worker，复杂度必须低于 Luna Worker。

## 5. 安装范围

AgentPorter 统一描述三种 scope：

- `user`：当前操作系统用户全局可见；
- `project`：仅当前仓库或工作区可见；
- `host`：另一台独立运行 Agent 的主机，必须显式指定并授权。

同一主机上的普通目录或 Git worktree 若共享相同用户配置根，不需要重复复制。SSH 远程目录只有在远端独立运行 Agent 时才需要安装；若 Agent 仍在本机运行、远端只是命令执行后端，则通常不需要。
